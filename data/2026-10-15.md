### [1] [Delta Tokenizer: Reference-Identical Tokenization of Session Deltas and Segment-Parallelism for Long Prompts on Multicore CPUs](https://arxiv.org/abs/2610.19801)
*Zhenyu Zhang,Zhichao Cao*

Main category: cs.CL

TL;DR: Delta Tokenizer 提供了一种针对长时间会话中增量更新的高效tokenizer方法，通过仅处理请求的增量部分，降低了初始令牌化时间（TTFT）和处理时间，特别适用于多核并行处理。


<details>
  <summary>Details</summary>
Motivation: 现有的tokenizer方法在处理长请求或会话时，因每次都重新进行完整的token化，导致CPU消耗较大且响应时间较长。Delta Tokenizer 旨在解决这一问题，通过仅重新处理请求中发生变化的部分，以更高效的方式处理请求。

Method: Delta Tokenizer 通过缓存早期的token序列，仅重新处理每个请求的增量部分。对于没有状态可以重用的长请求，它会选择在接近输入规则的位置进行分割，并利用多核并行处理来提高编码速度。系统内调度机制确保了小的增量更新可以在多个分块之间与短的增量更新并行进行。

Result: Delta Tokenizer 把一个会话转轮的令牌化时间缩短了大约40倍，相比Hugging Face的参考tokenizer，在16个内核上，分块并行路径编码400万字符的请求速度提高了8.2倍，且比LoPT快1.6到2.1倍。在SGLang内，它将中位数TTFT降低了59%，并且在高负载下减少了9.5倍的P99 TTFT，当长请求占用前端时，P99 TTFT进一步降低了23倍。

Conclusion: Delta Tokenizer 成功解决了在长会话中高效处理请求的问题，通过增量编码和多核并行技术显著提高了系统的响应速度和效率，特别是在多用户并发场景下具有显著优势。

Abstract: An agent that drives an LLM sends the model the same conversation again and again, and each turn adds only a little text at the end. Inference engines reuse the KV cache of the shared prefix, so only the new tokens pass through the model. However, tokenization has no such shortcut. The CPU front end of the serving engine converts every request back into token IDs from its first character, which lengthens the time to first token (TTFT) and consumes CPU on every turn.
  We present Delta Tokenizer, a CPU tokenization front end that tokenizes only the delta between a request and the previous request of the same session. It retains the earlier token sequence, encodes again only the appended text and the short tail whose tokens the append could affect, and joins the two only at a position the tokenizer's splitting rules themselves cannot move, which keeps the result exact. For long requests with no state to reuse, it cuts the text where practical tokenizers already keep neighboring pieces independent, encodes the pieces on several cores at once, and concatenates the outputs into the reference encoding, exactly. A shared CPU pool schedules these chunks together with the short incremental updates, so an update runs between two chunks rather than behind an entire long job.
  The incremental path shortens the tokenization of a session turn by roughly 40x relative to the Hugging Face reference tokenizer, and on 16 cores the chunk-parallel path encodes a four-million-character request 8.2x faster than a serial encode and 1.6-2.1x faster than LoPT. Inside SGLang, Delta Tokenizer reduces the median TTFT through the chat interface by 59% at 100K tokens and brings the P99 TTFT of agent sessions down 9.5x under load and 23x when long requests tie up the front end. Every output we checked matches the reference, among them 41.8 billion documents encoded by its fast encoder.

### [2] [How the Dirty Set Moves: Characterizing Schedule Reuse in Incremental Sparse Matrix Multiplication](https://arxiv.org/abs/2610.19489)
*Hunter Horne,Eric Spencer,Alex Henningfield,Arslan Bisharat*

Main category: cs.PF

TL;DR: 本文研究了增量稀疏矩阵乘法中基于tile的重用策略，发现直接列向增量更新比完整的重计算更快，但基于tile的重用策略尽管在779个工作负载中表现优于直接更新，但由于准备时间的节省而非缓存调度代码的额外空间，这取决于矩阵结构和脏集合的运动。


<details>
  <summary>Details</summary>
Motivation: 在稀疏矩阵乘法中，当矩阵保持固定而输入行发生变化时，通常可以仅基于更改的行来更新结果（称为脏集合）。因此，开发了一种基于tile的优化策略，通过仅准备一次调度并跨调用重用，以提高效率。

Method: 研究团队通过实验比较了直接列向增量更新和基于tile的重用策略在21个SuiteSparse矩阵和控制模式下的性能。

Result: 实验结果表明，直接列向增量更新的效率比最佳的完全重计算代码提高了2.1至8.2倍，尽管基于tile的重用策略在779个工作负载中表现优于直接更新。

Conclusion: 研究发现，重用策略的效益主要源自调度准备时间的节省，而额外的缓存空间很少有帮助，因为tile集很少在同一组之后再次出现。研究结论认为，矩阵结构和脏集合的移动模式决定了是否采用重用策略。

Abstract: Sparse matrices, in which most entries are zero, are central to scientific simulation, graph analytics and machine learning, and their multiplication with dense inputs is a core parallel kernel. In many applications the matrix stays fixed while only a few input rows change per step, so the result can be updated from those rows alone, which we call the dirty set. Sparse kernels often add a second optimization based on the inspector-executor principle, in which a tiled schedule is prepared once and reused across calls. However, when this reuse remains profitable as the dirty set moves is not well characterized. In this paper, we show that retained tiled execution rarely beats direct CSC in incremental sparse matrix multiplication, although incremental execution itself remains highly profitable. Across 21 SuiteSparse matrices and controlled patterns of motion, a direct column-wise incremental update is 2.1-8.2x faster than the best of eight full-recomputation codes, among them Intel oneMKL and PyTorch. Yet the same direct update outperforms a tiled executor that retains tile preparation and caches assembled schedules in 779 of 837 workloads. Separating reuse into per-tile preparation and cached schedules shows that the benefit comes from preparation; extra cache capacity seldom helps because a tile set rarely returns after a different one has intervened. Tiling is faster only when tiles merge many entries into each output write, a structural property that we predicted before measurement and confirmed on four held-out matrices of the same family. These results show that the structure of the matrix and the motion of the dirty set, rather than the sophistication of the schedule, determine whether reuse is profitable. We anticipate that our methodology and guidelines will help developers decide when to build schedule reuse into incremental sparse runtimes.
